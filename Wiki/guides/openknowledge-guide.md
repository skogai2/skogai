# Open Knowledge User Guide

This guide explains the setup that created the Skogai Wiki. It also covers the
`okn` CLI and the two `projects/ofk-*` submodules. Read it from top to bottom
once. Then use the sections as reference.

## 1. What happened in the setup

The setup ran these steps in order:

1. **Scaffold.** `okn scaffold` created a folder with a minimal bundle:
   `.openknowledge.toml`, `index.md`, `log.md`, `AGENTS.md`, `SPEC.md`, and a
   temporary `SETUP.MD`.
2. **Seed content.** The agent wrote the wiki pages: overview, architecture,
   projects, workflows, and this guide. It rewrote `index.md` and `AGENTS.md`
   for this repo.
3. **Validate.** `okn validate` first failed on five items. Sub-index
   frontmatter was not allowed, a log heading had the wrong date format, and a
   log line linked to a deleted file. The agent fixed all five. The second
   run passed.
4. **Search.** `okn search` ran one query and returned the matching section
   with its source path and line range.
5. **Complete.** `okn setup complete` registered the wiki as the connection
   `Wiki`. It installed project-level agent instructions for Codex and Claude.
   It left observation off.

The result is a bundle in `/home/skogix/skogai/Wiki`, plus three files in the
repo root that connect agents to it:

| File | Purpose |
| --- | --- |
| `.openknowledge/integration.toml` | Records which harnesses, skills, and knowledge base the setup installed. Tracks checksums of the managed files. |
| `.claude/skills/openknowledge/SKILL.md` | Instructions Claude Code reads. Generated by `okn`. |
| `.agents/skills/openknowledge/SKILL.md` | The same instructions for Codex. |

The managed block in those skill files is generated. Edit the text outside the
`openknowledge:managed` markers if you need project-specific guidance.

## 2. Core ideas

**Bundle.** A bundle is a folder of Markdown files. Each concept page starts
with YAML frontmatter that has at least a `type`. Reserved files do not need
that frontmatter: `index.md` (entry point and section indexes), `log.md`
(dated history), and `SPEC.md` (the pinned format spec). The format is
Open Knowledge Format (OKF), currently v0.2. Source: `Wiki/SPEC.md`.

**Rules.** A rule is a maintenance instruction, such as `project` or `writing`.
`.openknowledge.toml` lists the enabled rules. The `AGENTS.md` file repeats
them for agents. Run `okn prompt rules --list` for the full list.

**Registry.** `okn connect` gives a bundle a short key. Other commands accept
that key instead of a path. The registry file is at
`~/.config/openknowledge/registry.json`. `okn registry list` shows it.

**Managed and unmanaged.** A managed bundle has the OKF scaffold files and
validates against a spec. An unmanaged folder is ordinary Markdown. `okn search`
reports the status of each one (`managed` or `unmanaged`). The setup docs say
managed validation applies to bundles created by `okn setup` or `okn scaffold`.

**Search packet.** `okn search` returns a context packet, not a list of hits.
Each section comes with its file, heading, line range, score, relation, and
an `okf+sha256://` locator. The locator pins the content revision. Search is
local and deterministic. It does not call a model or an embedding service.

## 3. Commands

### Installed CLI

`okn` 0.13.0 is at `~/.local/bin/okn`. These are the top-level commands it
reports in `okn --help`:

| Group | Commands |
| --- | --- |
| Start here | `setup`, `search`, `validate`, `view` |
| Work locally | `agent`, `get`, `list` |
| Trust and govern | `audit`, `claims`, `evidence`, `eval`, `quality` |
| Query and interchange | `query`, `export` |
| Publish and operate | `mcp`, `connect`, `disconnect`, `registry`, `automation` |
| Advanced | `scaffold`, `prompt`, `ast`, `spec`, `version`, `telemetry` |

Every command accepts `--help`. Example: `okn search --help`.

### Commands the docs describe but 0.13.0 does not have

The `ofk-tools` docs (`projects/ofk-tools/README.md`) describe a newer
lifecycle. In that lifecycle, `okn check`, `okn review`, `okn publish`, and
`okn upgrade` are the main entry points. This installed binary does not
include them. Running `okn check` gives `unknown command`. Treat those
docs as the target design. Check `okn --help` before you rely on them.

## 4. The two ofk projects

### `projects/ofk-tools`: the okn CLI source

This submodule is the source of the `okn` CLI. Its `PRODUCT.md` describes the
intent: start with searchable Markdown, validate it, and retrieve a relevant
answer. Governance features (claims, evidence, CI, and runtime) are optional
layers added later. The product brief is in `PRODUCT.md`.

The repo is a pnpm and Go workspace. The CLI lives under `packages/cli`. Its
own user docs live under `Wiki/features/commands/`. That is the best source for
exact flags. Its `README.md` has install and lifecycle details. Its `AGENTS.md`
gives instructions for contributors.

### `projects/ofk-claude`: the Claude Code toolchain

This submodule is a separate project. It is the Claude Code plugin and skill
set for OKF. It provides agent skills (`okf`, `validate`, `visualize`,
`backfill`), a GitHub Action that validates a bundle in CI, and a read-only MCP
server. Its README lists install options.

It is not the `okn` binary. It works with OKF bundles, including ones that
`okn` created. The two projects share a format.

## 5. The wiki loop

Use this loop for any change to the wiki:

1. **Read.** Start at `index.md`. Follow only the links that match the task.
   Use `okn search "<wiki path>" "<query>"` to find sections fast.
2. **Edit.** Change or add Markdown pages. Keep the frontmatter valid. Update
   the section index when you add a page. Log the change in `log.md`.
3. **Validate.** Run `okn validate --spec 0.2 "<wiki path>"`. Fix all errors
   and avoidable warnings before you finish.
4. **Search.** Run one query that should find the change. Confirm the result
   matches the intent.
5. **Commit.** The wiki is plain files in the repo. Review the diff and commit
   with the rest of the repo's work.

Concrete commands for this wiki:

```bash
okn validate --spec 0.2 /home/skogix/skogai/Wiki
okn search /home/skogix/skogai/Wiki "which routes point to homes outside this repo"
okn list /home/skogix/skogai/Wiki
okn registry list
```

## 6. Claims and governance

The managed block in the project skill includes a claims workflow. It says to
run `openknowledge claims find` before a material factual change, and to
propose, apply, and validate claims. This wiki does not use claims yet. No
claim files exist, and the `claims` command is advanced. Skip that workflow
until you need evidence-backed facts. If you add it, the installed CLI
must have the `claims` subcommands. Check with `okn claims --help` first.

Note: the wiki's `AGENTS.md` does not mention claims. The project skill does.
Agents read both. Until claims are in use, the skill's claims section does
not apply, and agents should not run it for this wiki.

## 7. Glossary

| Term | Meaning |
| --- | --- |
| OKF | Open Knowledge Format. A folder of Markdown with YAML frontmatter. |
| Bundle | One OKF folder, such as `Wiki/`. |
| Concept | A Markdown page with frontmatter and a `type`. |
| Index | A reserved `index.md` that links to sections. |
| Log | A reserved `log.md` with dated `## YYYY-MM-DD` headings. |
| Rule | A named maintenance instruction. Enabled rules are listed in `.openknowledge.toml`. |
| Connection | A registry entry that maps a short key to a bundle path. |
| Managed block | Text between `openknowledge:managed` markers. `okn` regenerates it. |
| Locator | The `okf+sha256://` reference that pins a section to a content revision. |
